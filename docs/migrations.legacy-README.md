# Legacy SQL migrations (Phase 1-11, plus parity files post-Phase-12)

These files are archived from the pre-Alembic migration system. They
are NOT applied to fresh databases by `trip-ema` at startup — Phase 12
replaced the custom migrator with Alembic, and
`alembic_pkg/versions/0001_initial_schema.py` contains the squashed
equivalent of files 001-010.

## Why keep them?

Two reasons:

1. **Historical reference.** When something breaks in production and
   you need to know "what did migration 005 actually do?", the SQL
   is much easier to read than an autogenerated Alembic revision
   with equivalent ops.

2. **Parity test.** `tests/persistence/test_legacy_migrator.py`
   runs the legacy SQL files and the Alembic chain against two
   fresh databases and asserts the resulting table sets are
   identical. This guards against schema drift between the two
   paths. When you add an Alembic revision that creates a new
   table or alters an existing one in a way that changes the table
   set, add a matching `NNN_*.sql` file here to keep the test
   green. The matching SQL file MUST be bit-equivalent to the
   Alembic revision's DDL (same columns, types, constraints,
   indexes, grants, and seed data).

   This is why files numbered 011+ exist alongside the 001-010
   "true legacy" set: they are parity parallels of post-Phase-12
   Alembic revisions, not migrations the system ever applies in
   production.

## Parity-file catalogue

| File | Parallel of Alembic revision | What it creates / alters |
|---|---|---|
| `011_exchange_state.sql` | `0004_exchange_state` | `exchange_state` table + NSE seed row |
| `012_signal_backtest_runs.sql` | `0005_signal_backtest_runs` | `signal_backtest_runs` table + `etl_runs.exchange` column |

When adding a new Alembic revision that touches the table set
(`CREATE TABLE`, `DROP TABLE`) OR alters an existing table's columns
in a way that changes its shape, add a matching parity file and a
row to the table above.

## When are they touched?

Only by the parity test fixture (which calls
`trip_ema.persistence.migrator.apply_pending` against a fresh test
database). Never by production `trip-ema` startup; that path is
Alembic-only since Phase 12.

The `schema_migrations` table these files write to is still created
in production (for upgrade-bridge purposes) but no longer drives
migration flow.

## Upgrade path from a pre-Phase-12 database

A database that ran the legacy migrator through 010 will have:
- All schema objects files 001-010 create
- `schema_migrations` populated with versions 001 through 010

On first startup against such a database, `trip-ema` does the following:
1. Detects `schema_migrations` is populated through 010 (or higher —
   the bridge tolerates 011+ rows that may exist in test databases
   that ran the parity fixture)
2. Stamps Alembic's `alembic_version` table at `0001_initial_schema`
   (the squashed revision; matches the schema state already present)
3. Runs `alembic upgrade head` for anything past the squash —
   currently 0002 through the latest revision

No DDL is re-run. The `schema_migrations` table is preserved as
historical evidence of how the schema got to its current state.

See `trip_ema/persistence/alembic_bridge.py` for the stamp logic
and `docs/ARCHITECTURE.md` §3.14 for the runtime process boundaries
that motivated the Alembic transition.
