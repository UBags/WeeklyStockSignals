# Legacy SQL migrations (Phase 1-11)

These files are archived from the pre-Alembic migration system. They
are NOT applied to fresh databases — Phase 12 replaced the custom
migrator with Alembic, and `alembic_pkg/versions/0001_initial_schema.py`
contains the squashed equivalent of these files.

## Why keep them?

Historical reference. When something breaks in production and you
need to know "what did migration 005 actually do?", the SQL is
much easier to read than an autogenerated Alembic revision with
equivalent ops.

## When are they touched?

Never, by automated code. They are present for human reference only.
The `schema_migrations` table they reference is still created (and
populated for upgrades — see below) but no longer drives migration
flow.

## Upgrade path from a pre-Phase-12 database

A database that ran the legacy migrator through 010 will have:
- All schema objects these files create
- `schema_migrations` populated with versions 001 through 010

On first startup against such a database, `trip-ema` does the following:
1. Detects `schema_migrations` is populated through 010
2. Stamps Alembic's `alembic_version` table at `0001_initial_schema`
   (the squashed revision; matches the schema state already present)
3. Runs `alembic upgrade head` for anything past the squash (currently
   nothing; future migrations 0002+ go through Alembic from now on)

No DDL is re-run. The `schema_migrations` table is preserved as
historical evidence of how the schema got to its current state.

See `trip_ema/persistence/alembic_bridge.py` for the stamp logic
and `docs/ARCHITECTURE.md` §3.14 for the runtime process boundaries
that motivated the Alembic transition.
